# Функциональная спецификация (v1.0)

**Название:** Автоматический запуск пайплайнов на staging-окружении  
**Дата:** 2025-11-12  
**Автор:** Ilya Manyutin

---

## Цель

Обеспечить возможность единовременного запуска CI/CD-пайплайнов во всех 40 микросервисах на одном указанном тестовом staging-окружении.

---

## 1. Основная функция

Приложение должно позволять инициировать запуск пайплайнов в заданном наборе проектов в GitLab.

---

## 2. Входные данные

### 2.1. Список проектов

- Должен задаваться внешним файлом (например, `projects.txt` или `projects.json`).
- Для каждого проекта указывается его идентификатор (в любой однозначной форме — ID или полный путь).
- Для каждого проекта **может** указываться ветка или тег по умолчанию.

### 2.2. Параметры запуска

- **Обязательно** указывается имя целевого staging-окружения (например, `staging-07`).
- **Опционально** можно задать:
    - иное значение ветки/тега (единое для всех проектов),
    - дополнительные переменные CI/CD в формате `ключ=значение`,
    - максимальное число одновременных запусков (ограничение параллелизма).

### 2.3. Авторизация

- Учётные данные для доступа к GitLab (например, `PRIVATE-TOKEN`) должны задаваться отдельно от команды запуска — например, через переменную окружения (`GITLAB_TOKEN`).

---

## 3. Результат выполнения

### 3.1. Для каждого проекта:

- Инициируется запуск нового пайплайна с указанными параметрами.
- Возвращаются:
    - идентификатор запущенного пайплайна (номер),
    - прямая ссылка на него (`https://gitlab.com/.../pipelines/<id>`).
- При ошибке — указываются:
    - проект,
    - причина (`не найден`, `ошибка доступа`, `неверные параметры` и т.п.).

### 3.2. Общий результат:

- Выводится итог:
    - сколько проектов обработано,
    - сколько успешно запущено,
    - сколько завершилось ошибкой.
- Код возврата:
    - `0`, если все пайплайны запущены успешно;
    - ненулевой код в противном случае.

---

## 4. Ограничения поведения

- Приложение **не должно** ожидать завершения пайплайнов — только инициировать их.
- Не должно изменять состояние проектов (ветки, теги, файлы и т.д.).
- Не должно запускать пайплайны в проектах, не входящих в заданный список.
- Не должно кэшировать или модифицировать список проектов без явного указания.

---

## 5. Требования к использованию

- Должна быть предусмотрена возможность **ручного запуска** (например, через CLI).
- Должна быть поддержка **автоматического запуска** из скрипта или по расписанию (без интерактива).
- Все параметры, влияющие на поведение, должны задаваться **явно** — без «магических» значений по умолчанию, за исключением данных из конфигурационного файла проектов.

---

## 6. Безопасность и надёжность (функциональный уровень)

- Запуск должен быть **идемпотентным**: повторный вызов с теми же параметрами не приводит к непредсказуемым последствиям (например, дублирующиеся пайплайны — допустимы, но не критичны; главное — отсутствие побочных эффектов).
- При частичном сбое должна быть возможность **повторить запуск только для неудачных проектов** (например, через фильтрацию вручную или с помощью утилиты-обёртки).
- Секреты (токен/пароль) **не должны** появляться в:
    - логах,
    - stdout/stderr,
    - аргументах командной строки.
